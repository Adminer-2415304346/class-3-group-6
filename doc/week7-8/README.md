### 2.1 统一静态扫描

在仓库根使用独立工具Python环境，安装 `tools/requirements-quality.txt` 后执行：

```powershell
python -m pip install -r doc/week7-8/tools/requirements-quality.txt
python doc/week7-8/tools/scan_app.py accounts baseline
# 本人完成实际改进和验证后：
python doc/week7-8/tools/scan_app.py accounts after
```

按本人任务单把`accounts`换成对应app。脚本固定Ruff 0.17.1、Bandit 1.9.4，使用仓库内`ruff.toml`和`bandit.yaml`。
Ruff选E/F/I/B/C90，行长100、复杂度10；Bandit启用全部检查且不以`nosec`隐藏发现。
扫描明确枚举本app业务Python，排除历史迁移、`test*.py`和`tests/`；包含管理命令与模板标签。
测试和迁移另列范围，不混入业务代码指标。脚本不导入Django、不自动修复，也拒绝覆盖已有证据目录。
每轮自动保存`ruff.json`、`bandit.json`、`manifest.json`，后者包含版本、参数、配置哈希、范围与源文件哈希。
工具自身返回1通常表示有发现；脚本把完整扫描成功与执行失败分开，不能仅看包装脚本退出0就写“零告警”。

工具依据：[Ruff检查与规则](https://docs.astral.sh/ruff/linter/)、[Ruff配置](https://docs.astral.sh/ruff/configuration/)、[Bandit命令行](https://bandit.readthedocs.io/en/latest/man/bandit.html)。
课件中的SonarQube插件与Gitee是工具示例，本组现有GitHub仓库可继续使用；不声称执行了这些未使用工具。

### 3.1 实际阅读路径与人工分析

1. 文章读取：`urls.py → IndexView/ArticleDetailView → Article/Category/Tag → article模板及blog_tags`。
   首页筛`type='a', status='p'`；独立页面也走详情路由；分类与归档的类型筛选与首页不同。
2. 评论展示：`ArticleDetailView.get_context_data → Comment父评论分页/预加载 → Article.comment_list → query模板标签`。
   返回值保持QuerySet，递归模板依赖`.filter()`；计数、顶层分页、子评论预加载是不同用途。
3. 配置与缓存：`BlogSettings/Admin → save → 清共享缓存`；`seo_processor → 导航/配置缓存 → 请求域名及年份`。
   后台批量`update`与单条`save`的信号行为不同，不能据模型保存逻辑推断批量操作也刷新缓存。
4. 搜索及维护：`apps.ready → 搜索后端检查`、`search_indexes → 已发布批量索引`、`documents/management commands → 外部索引/头像/推送`。
   ES配置启用时导入即可外呼；维护命令具有真实写入或外发副作用，本轮仅阅读/注释，未执行。
5. 模板与插件：Markdown转换、摘要、Hook输出、Vite manifest和高亮；分别检查纯文本、HTML和属性值边界。

### 3.2 已完成的行为改进

| 编号 | 改动前 | 当前行为与验证 |
| --- | --- | --- |
| B01 草稿详情 | 匿名直接按ID访问草稿可得到200及正文，既有测试接受多个状态码。 | 公开详情只取已发布记录；已认证、有效超级用户保留后台草稿预览。普通作者、普通staff、未激活超级用户不能预览；已发布独立页面继续可读。两条旧宽泛断言收紧为404。 |
| B02 清缓存 | 任何访客GET/POST均可触发全站缓存清理。 | `/clean`只允许POST，强制CSRF并检查有效超级用户；GET为405，越权POST为403，有效管理操作只清理一次。全仓未找到依赖原GET调用的界面。 |
| B03 搜索高亮 | 对原文本反复替换后`mark_safe`，可保留script/解码后的HTML，重复词还会匹配新插入的mark标签。 | 只扫描原文一次，先转义文本/匹配段，仅由框架生成mark标签；重复词去重，优先较长匹配。 |
| B04 头像标签 | 将OAuth头像URL直接插入src后标为安全，引号可突破属性。 | `format_html`按属性值转义URL，尺寸显式转整数；验证恶意引号不能注入事件属性。 |

**缓存候选的处理**：空评论第二次读取会重查数据库，最初候选为`if value is not None`。
独立复核实际复现：空缓存建立后，后台批量启用首条评论不发`post_save`，会导致该优化长期复用空集合。
因此该优化已撤回，保留原重查语义；增加“空集→批量审核首条→立即可见”回归，把失效机制完善交给WZY与SZX/GCY协作。
不能把早期失败日志中的空缓存性能断言记成最终已完成优化。

### 3.4 源码注释和后续规范

18个非空业务文件均补了本周`# SZX（第7—8周）：`说明，覆盖模块、关键方法与核心块。
112行带本周署名前缀的业务注释，另有1行同组续行，合计113个物理注释行，其中2行是既有详情说明修订。

16个仅注释业务文件与基线AST一致；真正功能修改只在`blog/views.py`与`blog/templatetags/blog_tags.py`，测试修改另列。

可汇入全组规范的建议：

1. 所有有副作用的HTTP入口明确方法、身份/权限和CSRF；读取公开对象时按业务状态筛选。
2. 区分纯文本、HTML、属性与script上下文；优先模板自动转义、`format_html`或适合该上下文的框架API，禁止仅靠`mark_safe`声称安全。
3. 缓存必须约定空值、缓存键和失效路径；测试单条保存、批量更新及删除，不能只测命中性能。
4. 新缺陷回归必须在修复前暴露问题；权限与错误状态使用明确断言，避免多个状态均算成功。
5. 导入/启动避免业务库写入和网络外呼；外部依赖通过显式初始化与可替换边界接入。
6. 署名注释说明职责、理由和限制；保留历史作者，按文件区分本周新增与修订。
7. 扫描固定版本、配置及范围，先复核再改；告警数变化、误报与待办分别解释。
8. 长函数按职责拆分；异常处理捕获可处理异常并给出可观察的结果，不吞错误后打印成功。
