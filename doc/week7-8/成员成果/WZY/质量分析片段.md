## 一、模块概况

`comments` 是博客的评论与表情互动模块，职责边界：

- 评论提交：`CommentPostView`（登录保护 + CSRF + 表单校验 + 文章开关检查 + 父评论归属 + 审核开关）。
- 表情互动 API：`CommentReactionView`（GET 公开读统计，POST 登录后切换 8 种 emoji，按 comment/user/reaction_type 三元组唯一）。
- 通知：`send_comment_email`（给评论作者/父评论作者发邮件，独立于提交流程，由保存信号调用）。
- 模板标签：`parse_commenttree`（评论树递归）、`show_comment_item`（评论 UI 片段）。
- 依赖边界：只依赖 `blog.Article`、`blog.BlogSettings`、`accounts.BlogUser`、`djangoblog.utils/base_views`；不反向修改其它 App。

### 技能正例（核实后成立）

| 正例 | 证据 | 适用条件 |
|---|---|---|
| 登录与 CSRF：提交继承 `AuthenticatedFormView`，反应 POST 显式 `is_authenticated` 判断 | `views.py:18`、`views.py:102-106` | 表单视图默认 CSRF；手写 View 也依赖全局 CSRF 中间件 |
| 三元组唯一约束防重复点赞 | `models.py:148` `unique_together=['comment','user','reaction_type']` + `get_or_create` 切换 | `get_or_create` 依赖该唯一约束保证并发下不重复插入 |

| 公开读取限定 `is_enable=True` | `views.py:90/108` `get_object_or_404(Comment, id=…, is_enable=True)` | 未公开评论既不展示也不可点赞 |

### 缺陷/风险

| 编号 | 问题 | 证据 | 最小触发/影响 | 验证办法 |
|---|---|---|---|---|
| R1 | **跨文章回复**：回复的 `parent_comment` 未限定同文章 | `views.py:69-72` `Comment.objects.get(pk=…)` 未按 `article=` 过滤 | 恶意构造父 ID 可让 A 文章评论挂到 B 文章父评论，树结构错乱 | 手工构造跨文章父 ID POST；断言被拒 |
| R2 | 无效 `parent_comment_id` 触发 500 | `views.py:69-72` `Comment.objects.get` 无 DoesNotExist 处理 | 传不存在/其他文章的父 ID → 未捕获异常 → 500 | POST 无效父 ID，断言 404/400 而非 500 |
| R3 | 关闭文章直接 `raise ValidationError` 未捕获 → 500 | `views.py:55-56` | `comment_status='c'` 时提交评论 → 异常冒泡到视图层 → 500，错误反馈差；`article.status=='c'` 为死代码（status 仅 'd'/'p'） | 建关闭评论的文章 POST，断言友好响应 |
| R4 | `get_reactions_summary` 查询次数偏高（N+1 级） | `models.py:80-103`：1 次分组统计 + 每 emoji 1 次 user 查询 + 已登录时每 emoji 再 1 次 exists，约 1+8+8=17 次/条 | 文章页多评论 + 8 emoji → 查询数随评论数线性放大 | `assertNumQueries` 对比优化前后 |
| R5 | 批量启停不触发信号/缓存失效 | `admin.py:9-13` `queryset.update` | 批量审核/关闭后页面评论缓存可能不刷新（与组长问题同源） | 批量动作后复核页面与侧栏缓存 |
| R6 | 评论树递归逐节点查询 | `templatetags/comments_tags.py:20` `commentlist.filter(parent_comment=c,…)` 每节点一次查询 | 深层/大量评论页面查询数高 | `assertNumQueries`；考虑一次性加载按 parent 分组 |
