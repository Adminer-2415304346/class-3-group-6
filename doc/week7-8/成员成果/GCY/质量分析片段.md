## 1. 已确认的两条完整调用链

### 调用链 A：列表页查询 → 精细化缓存 → 信号清理
```
blog/views.py ArticleListView(CachedListViewMixin, ...)
  → mixins.CachedListViewMixin.get_queryset()
      → get_queryset_from_cache(cache_key)          # 命中直接返回
      → get_queryset_data()                          # MISS 时查询并 cache.set
  → blog/views.py get_optimized_article_queryset()   # select_related/prefetch_related 预取
  → djangoblog/utils.py cache（LocMem 或 Redis，见 settings.CACHES）
  → blog/models.py Article.post_save/post_delete
      → djangoblog/blog_signals.py model_post_save_callback
          → 精细化缓存清理（article 各字段键、category/tag/sidebar 键、get_blog_setting 等）
```
关键点：`update_fields == {'views'}` 时提前返回，浏览量局部更新不清理缓存；批量 `QuerySet.update()` 不触发 post_save，需业务层另行处理。

### 调用链 B：评论通知 → 信号 → 线程发邮件 → 发送日志
```
comments/views 提交评论 → comments/utils.py send_email(...)
  → djangoblog/utils.py send_email()
      → blog_signals.send_email_signal.send(...)
          → send_email_signal_handler()
              → _thread.start_new_thread(send_comment_email, ...)   # 异步，尽力而为
              → EmailMultiAlternatives 发送 + EmailSendLog 记录（失败时仅记录）
```
关键点：异步线程不 join、异常内部消化，邮件送达不保证；TESTING 环境不执行真实发送。

## 3. 代码设计

| 编号 | 位置 | 现象 | 核实结论 |
|---|---|---|---|
| DS-01 | `mixins.py` TimeStampedModel.save | `update_fields` 传参时自动补 `updated_at`；空集合 `update_fields=[]` 不补 | 合理设计；批量 `QuerySet.update()` 不触发 save() 的边界已在注释中说明 |
| DS-02 | `utils.py` cache_decorator | 用哨兵 `'__default_cache_value__'` 区分"返回 None"与"未命中"，避免空结果缓存穿透 | 合理设计；与 `CachedListViewMixin`（空结果不缓存，反复查库）策略不一致，见问题 P-02 |
| DS-03 | `settings.py` HAYSTACK 后端选择 | `if 'ELASTICSEARCH_DSL' in locals()` 依赖模块级变量是否定义 | 隐式分支，import 时执行，运行时改环境变量不生效；已在注释中说明 |
| DS-04 | `settings.py` CACHES | 默认 LocMem，设 `DJANGO_REDIS_URL` 才切 Redis | 多 worker 部署须用 Redis，否则信号清理只命中单进程；部署约束，非代码缺陷 |
| DS-05 | `plugin_manage/` | BasePlugin 定义契约，loader 扫描实例化，hooks 注册/触发解耦，业务代码显式触发 | 插件体系边界清晰：注册（启动时）与执行（业务调用点）分离，单插件异常被吞不影响主流程 |
| DS-06 | `elasticsearch_backend.py` vs `whoosh_cn_backend.py` | ES 后端在 search 内固定 `status='p' and type='a'`；Whoosh 后端依赖索引时数据范围，页面过滤由调用方负责 | 两后端"可见文档过滤"的执行位置不一致，属后端差异点，改动需两侧同步（已注释） |
| DS-07 | `admin_site.py` has_permission | 后台硬性 `is_superuser`；`logentryadmin.has_change_permission` 中 `has_perm('admin.change_logentry')` 分支实际不可达 | 权限语义冗余但无害；LogEntry 只读设计（禁增删、禁 POST 修改）意图明确 |

## 7. 编码规范建议（供《Python语言编码规范》参考，非全组决议）

1. **主要目的**：消除"命名空间不可追溯"与"异常面过大"两类常见隐患，降低多成员协作时静态检查误判。
   **适用范围**：共用层模块导入、缓存工具、信号处理、外部 HTTP 调用。
   **分类规范**：禁止无边界星号导入（`from x import *`），统一改显式导入；`except:` 必须收窄为具体异常类型。
2. **主要目的**：保证缓存读写的可观测与一致性。
   **适用范围**：`utils.py` 缓存装饰器、`mixins.py` 列表缓存、`blog_signals.py` 缓存清理。
   **分类规范**：空结果缓存统一采用哨兵值方案（区分"未命中"与"空结果"）；缓存键命名集中到 `constants.py`，键格式发布后不得随意改动。
3. **主要目的**：外部依赖调用必须可超时、可降级。
   **适用范围**：百度推送、头像下载、邮件发送等所有 `requests`/SMTP 外部调用。
   **分类规范**：所有 `requests.*` 显式传 `timeout`；外部通知类调用一律"尽力而为"，失败仅记日志不抛给主流程。
4. **主要目的**：安全敏感配置不落入代码。
   **适用范围**：`settings.py` 密钥、允许主机、检索/缓存后端选择。
   **分类规范**：`SECRET_KEY` 生产必须来自环境变量，禁止硬编码默认值；后端选择用显式开关替代 `locals()` 隐式判断；`ALLOWED_HOSTS` 生产收紧。
