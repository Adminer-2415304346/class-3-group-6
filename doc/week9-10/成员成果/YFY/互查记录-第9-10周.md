## 2. O91 state 绑定与一次消费

### 核实结果

| 核查项 | GZX 报告 | 实际核实 |
| --- | --- | --- |
| state 生成时机 | `oauthlogin` 每渠道生成随机 state 并写入会话 | `secrets.token_hex(32)`，写入 `request.session` 与 `OAuthLoginState`（`update_or_create`，按浏览器上下文+渠道唯一） |
| 有效期 | 300 秒 | `OAUTH_STATE_TTL_SECONDS` 默认 300，会话与数据库双侧校验 |
| 绑定浏览器 | state 绑定当前浏览器会话 | `browser_context` 取自会话并入库；会话中缺失/不一致即 403 |
| 回调校验顺序 | 先校验再换 token | `authorize` 依次校验会话 state、数据库条件更新消费，之后才调用 `get_access_token_by_code` |
| 一次消费 | 旧回调被拒且新 state 仍可用 | `OAuthLoginState.objects.filter(...).update(consumed=True)` 条件更新；会话侧同步 pop；重复回调 403 |
| 渠道不符 | 拒绝 | 会话按渠道存 state，`channel` 不同则取不到，403 |
| callback 与 next | 使用后台配置 callback，不通过任意参数传 next | 各渠道 `get_authorization_url` 使用 `self.callback_url`；next 取自发起时会话，`get_redirecturl` 已在 `oauthlogin` 做站内与白名单校验 |
| 渠道覆盖 | 五个已启用渠道均支持 state | `WBOauthManager`、`GoogleOauthManager`、`GitHubOauthManager`、`FacebookOauthManager`、`QQOauthManager` 的 `get_authorization_url(self, nexturl='/', state=None)` 均拼接 state |
| 禁用渠道 | 不发起外呼 | `get_config()` 过滤 `is_enable=True`；`get_manager_by_type` 在 `client_id` 为空时返回 None，`oauthlogin` 直接回首页 |
| 错误与日志 | 失败返回 502，不泄露敏感信息 | `RequestException`/`OAuthAccessTokenException` 捕获后 502；日志仅记录渠道与异常类型 |
| 超时 | 第三方请求有超时 | `OAUTH_HTTP_TIMEOUT = 10`，`do_get`/`do_post` 均显式 `timeout` |

### 发现

- state 在数据库与会话双写，消费以数据库条件更新为准，会话删除为辅助，跨进程/多实例下方向正确。
- 同一浏览器同一渠道再次发起会 `update_or_create` 覆盖旧 state，旧回调随后失效，符合“最新一次授权”语义。
- `authorize` 对已绑定账号校验 `is_active=True`，停用账号返回 403，OAuth 登录路径不再绕过激活状态。

### 结论

**O91 实现真实、行为与任务单一致**，测试可复现，可进入集成。

## 3. O92 邮箱归属与一次性绑定

### 核实结果

| 核查项 | GZX 报告 | 实际核实 |
| --- | --- | --- |
| 待绑定记录 | 新增 PendingBinding，关联 OAuthUser、邮箱、nonce、浏览器上下文、消费状态 | `PendingBinding` 字段齐全，`nonce` 唯一；迁移 `0004_pendingbinding` 存在 |
| 绑定期限 | 600 秒 | `OAUTH_BIND_TTL_SECONDS` 默认 600，`TimestampSigner` 与数据库 `expires_at` 双重校验 |
| 签名内容 | 签名覆盖 oauthid、邮箱、nonce | `sign_object` 载荷含三者；`_read_binding_proof` 用 `unsign_object` 解析 |
| 旧链接兼容 | 旧无限期签名失效，旧限时签名在有效期内可确认 | 旧格式按 `id:email:nonce` 解析且要求数据库仍有同邮箱、未消费、未过期记录；签名盐固定 `week910.oauth.bind` |
| 篡改 | 隐藏 ID/邮箱/nonce 篡改不产生他人写入 | 表单 `oauthid` 与会话 `pending_oauth_id` 比对；签名不匹配 400；跨浏览器 403 |
| 已有同邮箱 | 不静默取得本地账号，需先登录该账号 | `_existing_email_owner` 要求 `request.user` 为该邮箱的有效账号，否则 403；未登录不会 `get_or_create` |
| 新邮箱 | 验证后才创建本地账号并绑定 | `emailconfirm` 事务内校验 PendingBinding → 创建账号 → 绑定 → 消费，成功后才 `login` |
| 取消/重发 | 作废旧证明 | `bindsuccess` POST：`cancel` 置 `consumed=True`；`resend` 先作废当前 nonce 再生成新 nonce 并重发 |
| 登录导致会话轮换 | 轮换 `session_key` 后仍可确认 | 测试 `test_T05` 在 `client.login()` 后继续走确认链接并通过；会话数据在 `cycle_key` 后保留 |
| 唯一性与并发 | 条件消费保证只成功一次 | `available.filter(consumed=False).update(consumed=True) == 1` 后才建号，重复点击仅一次成功 |

### 发现

- 邮箱绑定与 accounts 激活签名盐不同（`week910.oauth.bind` vs accounts 侧盐），互不可复用，隔离正确。
- 新账号用户名由邮箱 HMAC 派生（`oauth_<digest>`），避免用户名冲突；`create_user` 默认不可用密码，符合第三方账号场景。
- `emailconfirm` 在事务提交后再发送“绑定成功”邮件，发信失败不影响绑定结果（见 5.4）。

### 结论

**O92 实现真实、行为与任务单一致**，测试可复现，可进入集成。

### 5.3 【建议】补邮箱与重发确认邮件缺少发送频率限制

- `RequireEmailView` 在 `pending_oauth_until`（600 秒）内可反复提交任意邮箱，每次都会 `send_email`；`bindsuccess` 的 `resend` 同样无冷却。
- 风险：持有一个未绑定第三方账号的用户，可在窗口内对任意邮箱重复发确认信（邮件轰炸/骚扰），且每次会作废旧链接。
- 建议：复用 accounts A91 的冷却模式（按规范化邮箱 + 浏览器上下文缓存键），或在 `OAuthUser` 上记录最近发送时间并限制重发间隔。

### 5.4 【建议】`emailconfirm` 以 GET 完成建号并登录

- `@require_GET` 的确认链接直接创建账号并 `login`，邮件安全扫描器/链接预取可能先于用户点击消费一次性链接，用户随后打开会看到“链接已失效”。
- 建议：确认页先展示邮箱与操作按钮，由 POST 完成绑定；或在文档中明确该风险与规避方式。

### 5.5 【建议】失败分支的状态消费与发信异常

- `_consume_state` 在检查 `code` 之前完成 state 消费：提供方以 `error=access_denied` 回调（无 code）时 state 已被烧掉，用户需重新发起。方向保守，但错误页可提示“请重新从登录页发起”。
- 新建账号路径中，事务提交后发送“绑定成功”邮件若抛异常会返回 500，此时账号已建、绑定已消费，用户下次 OAuth 登录可直接进入；建议捕获发信异常并记录，避免整体 500。

### 5.6 【建议】过期待绑定记录缺少清理

- `PendingBinding` 仅在重发、取消或同一 OAuthUser 再次发起时被作废，无全局过期清理；与 `OAuthLoginState` 在 `oauthlogin` 顺带清理不同。
- 数据量小，当前不影响功能；可在后续维护任务中按 `expires_at` 批量删除。

## 6. 跨模块边界检查

- **邮箱唯一性**：`BlogUser.email` 仍未加唯一约束，oauth 绑定以 `email__iexact` 找归属并要求登录确认，已避免静默合并；但同邮箱仍可能对应多个本地账号（历史候选风险，保持开放）。
- **激活状态**：`authorize` 对已绑定账号校验 `is_active=True`，GZX 互查记录中“oauth 回调 `login` 绕过 `is_active`”的旧结论对当前版本已不成立，建议同步更新该条目。
- **签名盐隔离**：oauth 绑定盐与 accounts 激活/找回密码盐不同，互不可复用。
- **配置读取**：`OAUTH_STATE_TTL_SECONDS`、`OAUTH_BIND_TTL_SECONDS` 走统一 `get_maintenance_option`，与 accounts 维护配置入口一致。
