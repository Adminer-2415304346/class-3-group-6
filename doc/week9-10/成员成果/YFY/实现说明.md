## 1. 现象与目标

### A91 服务端验证码发送冷却

现象：发送接口 `/forget_password_code/` 只做邮箱格式校验，服务端没有频率限制；前端 `launcherAccount.js` 只是本地倒计时，绕过浏览器或开第二个窗口可以连续发信；成功返回纯文本 `ok`，格式错误也返回 200 纯文本。

目标：用 `RESET_SEND_COOLDOWN_SECONDS=60` 按规范化邮箱在服务端限制重复申请；冷却期返回 429 `rate_limited`、`Retry-After` 头和 JSON `retry_after`；拒绝时不发信、不覆盖旧码；投递失败可立即重试且不留下新码；前端只使用服务端剩余秒数。

### A92 验证码失败次数与挑战锁定

现象：`verify()` 只比较缓存中的码，没有失败计数；任何人只要知道邮箱就能反复提交错误码；表单错误提示不区分过期、错误、锁定等状态。

目标：同邮箱 + 当前挑战 + 当前浏览器上下文连续 5 次错误后锁定 900 秒；码有效期 300 秒，成功重置后立即消费；挑战绑定浏览器会话，避免任意访客凭邮箱锁死他人；缺邮箱、空码、其他字段非法不计真实尝试；`verify` 只读，消费单独执行；锁定期正确码也拒绝；过期、解锁、新挑战状态明确。

## 2. 方案与改动

### 2.1 `src/DjangoBlog/accounts/utils.py`

新增状态与缓存函数：

- `normalize_email()`：`strip().casefold()`，发送、冷却、写入、校验保持同一口径。
- `ResetContext(digest, challenge)`：浏览器上下文摘要 + 当前邮箱挑战标识。
- `get_browser_context()` / `get_reset_context()` / `remember_challenge()` / `forget_challenge()`：会话中的随机上下文标识与挑战绑定。
- `get_send_cooldown_remaining()` / `try_reserve_send()` / `release_send_cooldown()`：冷却占用、真实剩余秒数、失败释放。
- `get_code_remaining()` / `get_lock_remaining()`：按 `expires_at` 计算剩余时间，边界为 `now >= expires_at`。
- `verify(email, code, context=None)`：保留既有两位置参数调用；`context=None` 保持旧行为，HTTP 路径传入 `ResetContext` 后启用挑战绑定、锁定检查与失败计数。
- `set_code(email, code, challenge=None)`：缓存值改为 `{code, expires_at, challenge}`，TTL 从维护配置读取。
- `consume_code()` / `clear_attempt_state()`：成功消费时删除码并清理失败/锁定；`delete_code()` 保留为兼容入口。
- `_now()`：集中时钟入口，测试可替换，不需要 sleep。

缓存键（敏感标识只写摘要）：

```text

week910:accounts:reset-send:<sha256(规范化邮箱)>
week910:accounts:reset-failures:<邮箱摘要>:<浏览器上下文摘要>
week910:accounts:reset-lock:<邮箱摘要>:<浏览器上下文摘要>
```

会话键：`week910:accounts:browser-context`（随机上下文标识）、`week910:accounts:reset-challenges`（邮箱摘要 → 挑战标识）。

### 2.2 `src/DjangoBlog/accounts/views.py`

- `ForgetPasswordView.get_form_kwargs()`：把 `request` 传给表单，校验上下文才能绑定会话。

- `ForgetPasswordEmailCode.post()`：
  1. 邮箱格式非法 → 400 `invalid_email`；

## 3. 接口返回（实际实现）

```json
{"success": true, "code": "sent", "message": "验证码已发送", "data": {}, "retry_after": 60}
```

```json
{"success": false, "code": "rate_limited", "message": "验证码发送过于频繁，请稍后重试", "data": {}, "retry_after": 42}
```

- 400：`invalid_email`
- 503：`delivery_unavailable`
- 429：同时设置 `Retry-After: <秒>`

## 4. 状态流转

1. 新申请：占用冷却 → 发信 → 写码（300 秒）→ 绑定新挑战 → 清理该上下文失败/锁定。
2. 校验：码不存在/过期 → 锁定 → 挑战不匹配 → 码比较；`verify` 不删除码。
3. 第 5 次错误：写入锁定到期时间（900 秒），锁定期内正确码也返回锁定错误。
4. 成功：视图保存密码后 `consume_code` 删除码、清理状态、移除会话挑战；旧码再次提交按“已过期或不存在”处理。
5. 到期/解锁：按 `expires_at` 判断；新挑战会重置该上下文的失败计数。
6. 会话绑定：非申请挑战的浏览器提交错误码返回“验证码已失效，请在当前浏览器重新获取”，不计失败次数，无法锁死他人。

### 6.2 操作步骤与预期

1. 首次申请：POST `email=reset@example.com` → 200 `sent`，终端/LocMem 收到 1 封；码 300 秒有效。
2. 第二窗口重复申请：同一邮箱在 60 秒内再次 POST（包括另一个浏览器/Client）→ 429 `rate_limited`，`Retry-After` 与 JSON `retry_after` 一致，邮件数量不增加，旧码不变。
3. 错误次数达到上限：连续提交 4 次错误码 → 提示“还可尝试 4/3/2/1 次”；第 5 次 → 锁定 900 秒；此时提交正确码仍被拒绝。
4. 到期后恢复：等待/推进超过 300 秒后旧码提交 → “验证码已过期”；超过 900 秒锁定解除，重新申请新码后可正常重置。
5. 正常重置：正确码提交 → 302 到 `/login/`，密码更新，码被消费；再次提交旧码 → 200 且提示过期/不存在。
6. 会话绑定：原申请窗口提交正确码成功；另一个未申请该码的窗口连续错误提交只作用于它自己的上下文，原窗口仍可成功重置。

### 6.3 挑战/会话条件与参数

- 发送时生成随机挑战标识，写入码记录并绑定到当前会话；校验时必须匹配当前会话中的挑战。
- 失败计数与锁定按“邮箱 + 浏览器上下文”隔离，不按全局邮箱。
- 本轮测试参数：全部为生产默认值（300/60/5/900），未缩短；时间推进用测试时钟，不等待真实时长。

## 7. 已知边界

- `cache.add` 在单进程 LocMem 内原子；多进程/多实例的严格单航班取决于共享缓存后端（如 Redis），部署后需复核。
- 攻击者仍可通过反复申请新码覆盖旧码（受 60 秒冷却限制），但无法通过错误尝试锁定受害者上下文。
- 首次创建 `BlogSettings` 时共享代码会调用全局 `cache.clear()`；测试已先初始化站点配置，避免误清验证码状态。生产环境已有配置，正常不会触发。
- 锁定时长 900 秒大于码的 300 秒有效期，解锁后需重新申请新码。
