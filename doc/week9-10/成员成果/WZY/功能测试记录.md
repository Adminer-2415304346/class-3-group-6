## 2. 基线采集与失败原因（如实保留）

任务单给定的 baseline 命令原样执行时（`python doc/week7-8/tools/run_isolated_tests.py --result-json 证据/baseline-tests-raw.json comments.test_reaction_snapshot comments.tests comments.test_views comments.test_comment_business_logic comments.test_quality_r45 djangoblog.test_week910_configuration`）结果为 **60 项 / 7 failures / 0 errors / 0 skipped**：

- 失败点全部在 `blog/article_detail.html` 的 `{% compress %}`：模板标签在编译期 import `compressor.filters.base`，其中 `if system() != "Windows"` → `platform.system()` → `platform.win32_ver()` → `subprocess.check_output`；runner 为“禁止外部命令”打的补丁让它抛 `AssertionError`。
- 另一处触发点是 `djangoblog/error_views.py:51 render_error_page`。
- 与业务代码无关。尝试用 `COMPRESS_ENABLED`/`DEBUG` 覆盖无效：platform 探测发生在模块**导入期**，settings 覆盖来不及生效。
- 处置：本人证据目录新增包装器 `证据/run_isolated_tests_wzy.py`——在 runner 安装补丁**之前**预热 `import compressor.filters.base`，再用 `runpy.run_path` 委托官方 runner，参数和“failures/errors 必须为 0”的口径完全不变。共享 runner 一行未改。
- 结论：原始失败证据保留在 `证据/baseline-tests-raw.log`（完整 stdout/stderr）与 `证据/baseline-tests-raw.json`；经包装器的干净复跑为 `证据/baseline-tests.json`。

## 3.1 补测反馈的两处缺陷与回归用例

首次推送后被补测出两个真实缺陷，均已在本轮修复（业务修复提交 `bb058c4`、用例补充提交 `6be622e`）：

| 现象 | 根因 | 处置 | 对应用例 |
| --- | --- | --- | --- |
| 去掉首尾空格后刚好 2000 字的评论仍被拒绝 | `strip=False` 使字段层看到未去空白的原始值，而 `ModelForm` 按模型 `max_length=2000` 派生的 `MaxLengthValidator` 先于 `clean_body` 执行，带空格的 2002 字符被判超长；同一原因下超长提示是 Django 自带文案 | 摘掉字段级长度校验（`max_length=None`、过滤 `MaxLengthValidator`）、去掉 widget `maxlength`，长度只由 `clean_body` 按去空白后的值判定 | `test_c_t02_boundary_with_surrounding_spaces_accepted`、`test_c_t02_2001_chars_rejected`（新增文案断言） |
| 两个请求都通过前置检查时，后者覆盖限频状态、两条评论都入库 | `_reserve` 用 `update_or_create`；限频 `state_key` 固定，冲突时它改写已有行并返回成功，相当于把抢占结果覆盖掉 | `_reserve` 改为 `create`（只插入不更新），冲突即 `IntegrityError` → `None`，按重复/过频拒绝 | `test_c_t06_concurrent_interval_reserve_does_not_overwrite`、`test_c_t06_both_prechecks_pass_only_first_persists` |

修复后复跑：隔离测试 90 项 / 0 failures / 0 errors / 0 skipped（comments 80 / djangoblog 10），扫描 12 文件 ruff 0 / bandit 0；`after-tests.*` 与 `after-scan/` 均为这次复跑的输出。
