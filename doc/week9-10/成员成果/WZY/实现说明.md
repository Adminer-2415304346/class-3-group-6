## 2. C91 实现细节

**原行为**：`CommentForm` 的 `body` 由 `ModelForm` 直接生成，`max_length=300`（模型约束），空白正文会被 Django 字段层 `strip` 后判为“必填项”，超长正文只给出 Django 默认长度提示；`CommentPostView.get()` 用 `get_object_or_404(Article, pk=...)`，草稿文章也能进入评论流程；表单错误回显依赖 `article_detail.html` 是否渲染评论表单，关闭评论时用户看不到任何提示。

**本轮行为**：

1. 正文规则统一为“去首尾空白后 1—`COMMENT_MAX_LENGTH` 字符”：
   - `CommentForm.__init__` 里 `self.fields['body'].strip = False`，纯空白正文走到 `clean_body`，得到本组提示“评论内容不能为空，请填写后再提交.”，而不是字段层的“这个字段是必填项。”；
   - `clean_body` 去首尾空白后返回，入库值为去空白后的正文；超限提示“评论内容最多 %(max)d 个字符，当前为 %(actual)d 个字符.”，其中 `max` 取自 `get_maintenance_option("COMMENT_MAX_LENGTH")`；
   - `Comment.body` 的 `max_length` 由 300 调整为 2000，与阈值默认值对齐（注释已写明只参与模型/表单校验，不改 MySQL `TEXT` 物理长度）；
   - 字段层的长度校验整体摘掉（`body_field.max_length = None`、从 `body_field.validators` 中移除 `MaxLengthValidator`、去掉 widget 的 `maxlength` 属性），长度只由 `clean_body` 按去首尾空白后的值判定。原因：`ModelForm` 按模型 `max_length` 派生字段级校验且先于 `clean_body` 执行，而 `strip=False` 让该处看到的是未去空白的原始值，会出现两个错误——带前后空格、去空白后刚好 2000 字被判超长误拒；真正超长时提示是 Django 自带的“确保该变量包含不超过 2000 字符”，不是本组文案。
2. 目标文章校验：新增 `get_target_article()`，`get_object_or_404(Article, pk=..., status='p')`，草稿（`status='d'`）与不存在文章统一按 404；`get`、`form_invalid`、`form_valid` 全部改用该入口。已发布的独立页面（`type='page'`）沿用原评论规则。
3. 错误可见性：
   - 公开文章：`templates/comments/tags/post_comment_modern.html` 补 `form.non_field_errors` 红色错误块与 `parent_comment_id` 错误块（`article_detail.html` 实际 include 的是该模板，不是 `post_comment.html`）；旧模板 `post_comment.html` 同步补同样的两块兜底；
   - 关闭评论 / 站点级评论开关关闭时：`article_detail.html` 的条件是 `article.comment_status == 'o'` 且 `OPEN_SITE_COMMENT` 为真才渲染表单，此时回显文章页等于“错误不可见”。`form_invalid` 判断该条件后改用 `templates/comments/post_comment_error.html`（标题“评论未能提交”，列出非字段/正文/父评论错误，附“返回文章页”），状态码仍为 200。
4. 父评论校验保持原口径（`parent_comment_id__article_id=article.pk`），无效/跨文章父ID 仍为表单错误，不产生 500。

## 3. C92 实现细节

**原行为**：评论发布没有任何时间维度的保护，同一用户可以无限次提交同一正文。

**本轮行为**（事务性状态记录，不使用缓存原子操作，因此不存在“本地能用、多进程失效”的夸大保证）：

1. 新增模型 `CommentPostState`：`user`（FK，`on_delete=CASCADE`）、`scope`（`interval` / `duplicate`）、`state_key`（sha256 十六进制 64 字符）、`expires_at`、`updated_at`；唯一约束 `UniqueConstraint(user, scope, state_key)`（`name='uniq_comment_post_state'`），索引 `Index(fields=['scope', 'expires_at'])`（`name='idx_cmt_state_expire'`）。
2. 新增 `comments/post_guard.py`：
   - `normalize_comment_body`：去首尾空白并把连续空白折叠为单空格，**只用于计算重复摘要，不改变入库正文**；
   - `duplicate_state_key(article_id, body, parent_comment_id)`：sha256(文章 + 规范化正文 + 回复目标)；
   - `interval_state_key()`：固定键，表示“该用户的发布冷却”；
   - `_remaining_seconds`：向上取整、至少 1 秒，用于给用户可读的剩余时间；
   - `_prune_expired`：只删本用户已到期状态行，避免状态表无限增长；
   - `_reserve`：**只插入不更新**（`CommentPostState.objects.create(...)`），包在 `atomic()` 内，唯一约束冲突捕获 `IntegrityError` 视为并发抢占失败（返回 `None`）。不能用 `update_or_create`：限频用的是固定 `state_key`，`update_or_create` 遇到已存在的行会改写 `expires_at` 并返回成功，等于让后到请求无声覆盖先到者的抢占结果，两个都通过前置检查的请求会各自入库（补测已复现，见 `bb058c4`）；`_prune_expired` 已先清掉到期行，因此插入失败只可能是并发抢占；
   - `check_and_reserve`：**先判重复、再判过频**；重复命中报“该内容与你在 %d 秒内的评论重复，请在 %d 秒后再试.”，过频报“评论提交过于频繁，请在 %d 秒后再试.”；两个窗口分别取 `COMMENT_DUPLICATE_WINDOW_SECONDS`（120）与 `COMMENT_INTERVAL_SECONDS`（30）。
3. `CommentPostView.form_valid`：`with transaction.atomic():` 内先 `check_and_reserve(...)`，再 `comment.save(True)`（沿用原有“保存 + 通知”链路）；捕获 `CommentPostRejected` 后 `form.add_error(None, message)` 走 `form_invalid` 回显。**状态行与评论写入同事务**，任一失败一起回滚，不留冷却、不发邮件、不触发缓存失效。
4. 冷却与表情互不影响：表情切换走 `CommentReaction` 接口，不经过 `CommentPostView`，因此不受评论冷却限制（有用例覆盖）。
5. 隔离性：重复键含用户、文章、回复目标，另一用户或另一文章互不影响；冷却按“用户”维度，符合任务单“全用户间隔按约定独立验证”的口径。
